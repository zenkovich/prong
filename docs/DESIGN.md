# Prong — функциональный дизайн

Кроссплатформенный git-клиент в духе Fork: быстрый, плотный, «десктопный» интерфейс с графом коммитов, списком изменений и диффами. UI на React Native, git-движок — отдельный слой, одинаковый для всех платформ.

Статус документа: v0.2 (2026-10-19). Этап 1 (прототип UI на моках) завершён; этап 2 начат: реальный git-движок как локальный сервис, приложение работает с настоящими репозиториями.

---

## 1. Цели и границы

**Цели**

- Повторить рабочую модель Fork: один репозиторий = одна вкладка, слева навигация (Changes / All Commits / Branches / Remotes / Tags / Stashes), в центре граф, снизу/справа детали и дифф.
- Один код UI для macOS, Windows, Linux (и, как побочный эффект, web-прототип для демо).
- Быстрый отклик на репозиториях в десятки тысяч коммитов: виртуализированные списки, инкрементальная загрузка графа, кеширование диффов.
- Аккуратный визуальный стиль: тёмная и светлая тема, плавные переходы панелей, анимация появления строк графа и хунков диффа, без «мобильных» паттернов.

**Вне scope первой версии**

- Interactive rebase с редактированием сообщений в текстовом редакторе (делаем через UI-список).
- Git LFS, submodule-операции кроме отображения статуса.
- Code review / PR-интерфейс GitHub (только auth и клонирование по списку репозиториев).

## 2. Платформы и архитектура

```
┌──────────────────────────────────────────────────────────┐
│  UI (React Native + TypeScript)                          │
│  screens / components / state (zustand) / theme          │
├──────────────────────────────────────────────────────────┤
│  GitClient API (TS-интерфейс, платформо-независимый)      │
│    openRepo, log, status, diff, stage, commit, push ...   │
├─────────────────────────┬────────────────────────────────┤
│  MockGitClient (этап 1) │  ProcessGitClient (этап 2)      │
│  фикстуры в памяти      │  spawn `git` CLI + парсер       │
│                         │  porcelain-вывода               │
└─────────────────────────┴────────────────────────────────┘
```

**Платформы UI**

| Платформа | Рендер | Статус |
|-----------|--------|--------|
| Web (браузер) | react-native-web через Expo (Metro) | этап 1, прототип и демо |
| macOS | сейчас: Swift-оболочка AppKit + WKWebView вокруг web-сборки, движок в бандле (`macos/`); далее: react-native-macos | этап 2, основная цель |
| Windows | react-native-windows | этап 3 |
| Linux | нет зрелого RN-рендера; запасной вариант — web-сборка внутри Tauri/Electron | этап 4 |

Expo выбран ради web-сборки из коробки и Expo Modules. macOS в Expo пока экспериментальна (react-native-macos отстаёт от core RN на 1–2 минорных версии; `expo prebuild --platform macos` ещё не поддерживается), поэтому macOS-проект создаётся через `react-native-macos-init` в bare-режиме, а UI-код переиспользуется без изменений.

**Git-движок (реализовано, этап 2)**

Локальный сервис `prong/server` на Node + TypeScript: запускает системный `git`, парсит porcelain-вывод и отдаёт результат по HTTP (`127.0.0.1:8790`) с потоком прогресса длинных операций (SSE). Приложение общается с ним через интерфейс `GitClient` (`src/git/GitClient.ts`, реализация `HttpGitClient`); мок-клиент остаётся для демо и статической сборки. Слой `src/state/live.ts` подменяет действия стора для «живых» репозиториев: каждая мутация вызывает сервис и перечитывает снимок (`snapshot`: лог до 500 коммитов `--topo-order --all`, refs с upstream-трекингом, remotes, stash list, status porcelain v2 + numstat), диффы и файлы коммитов грузятся лениво при выборе. В macOS-сборке сервис поставляется рядом с приложением (bundled Node или скомпилированный бинарь) и стартует как дочерний процесс; тот же сервис выполняет команды агента.

Состав сервера: `src/git/run.ts` (spawn, прогресс по stderr, неинтерактивное окружение), `src/git/parse.ts` (log, for-each-ref, status v2 -z, unified diff → хунки, numstat, stash list), `src/git/repo.ts` (все операции: stage/unstage/discard по файлам и хункам через `git apply --cached`, commit/amend, fetch/pull/push с прогрессом, ветки, теги, merge, rebase и интерактивный rebase через `GIT_SEQUENCE_EDITOR` с `reword` → `exec git commit --amend`, cherry-pick, revert, reset, stash, clone, init, blame, картинки до/после как data-URI), `src/api.ts` (роутер, реестр репозиториев в `~/.prong/repos.json`, SSE). Тесты: vitest, парсеры на фикстурах, интеграционные на временных репозиториях с bare-remote, HTTP-API с проверкой потока событий.

Запасные варианты движка, если производительности CLI не хватит:

1. **Спавн системного `git`** через нативный модуль (Expo Module / TurboModule: `spawn(cmd, args, cwd, env) → {stdout, stderr, code}` + стрим для `clone`/`fetch` с прогрессом). Плюсы: 100 % совместимость с хуками, credential helpers, `.gitconfig`, ssh-agent; просто отлаживать; не нужно компилировать libgit2 под 3 платформы. Минусы: зависимость от установленного git (на macOS есть через Xcode CLT; на Windows — Git for Windows, ставим в инсталлятор).
2. libgit2 через нативный биндинг — быстрее на больших логах, но дороже в сопровождении. Оставляем как опцию для `log`/`diff`, если производительность CLI окажется недостаточной.

Парсинг: `git log --format=<поля с \x1f>` + `--parents` для графа; `git status --porcelain=v2 -z`; `git diff --no-color -U3 -z`; `git show`; `git stash list --format`; `git rebase --interactive` с `GIT_SEQUENCE_EDITOR` = собственный скрипт, который применяет todo, сформированный в UI.

**Состояние**: zustand-стор на репозиторий (`RepoStore`) + глобальный `AppStore` (список репозиториев, аккаунты, настройки, тема). Все git-операции идут через очередь задач с прогрессом (одна операция записи одновременно на репозиторий, чтение — параллельно).

**Хранение**: список репозиториев, настройки, кэш аватаров — JSON в папке данных приложения. Секреты (GitHub-токены, пароли ключей) — только в системном хранилище: macOS Keychain, Windows Credential Manager, libsecret на Linux.

## 3. Структура интерфейса

Главное окно (1280×800 минимум, тёмная тема по умолчанию):

```
┌─ Tabs: [repo A] [repo B] [+] ───────────────────────────────────────────┐
│ Toolbar: ⟳Fetch  ⇣Pull  ⇡Push  ◫Stash  ⌥Branch  ⤵Rebase  ⚙  [search]    │
├────────────┬────────────────────────────────────────────────────────────┤
│ Sidebar    │ Main                                                       │
│  Changes 3 │  (зависит от выбранного раздела сайдбара)                  │
│  All Cmts  │                                                            │
│ ─Branches  │  All Commits: граф + таблица (Description / Author / Date) │
│   main ●   ├────────────────────────────────────────────────────────────┤
│   feat/x   │ Details                                                    │
│ ─Remotes   │  Commit: заголовок, автор, хеш, родители, метки            │
│   origin   │  Files (tree/list) │ Diff                                   │
│ ─Tags      │                                                            │
│ ─Stashes   │                                                            │
├────────────┴────────────────────────────────────────────────────────────┤
│ Status bar: ветка, ahead/behind, прогресс текущей операции              │
└─────────────────────────────────────────────────────────────────────────┘
```

Разделители панелей перетаскиваются, положение запоминается на репозиторий. Все панели сворачиваются (⌘1…⌘4).

### 3.0 Воркспейсы

- Воркспейс — именованный набор репозиториев со своими открытыми вкладками (например `@work`, `@home`); аккаунты, SSH-ключи и настройки общие. Переключатель `@work ▸` слева в полосе вкладок открывает якорный поповер: строка на воркспейс с числом репозиториев и открытых вкладок, активный помечен `▸` и меткой current; ниже New / Rename / Delete, список воркспейсов со счётчиками на стартовом экране, команды в палитре (`Workspace: @home`).
- При переключении вкладки текущего воркспейса сохраняются и восстанавливаются при возврате; открытие репозитория из другого воркспейса переключает на него. Удаление воркспейса переносит его репозитории в соседний, на диске ничего не меняется.
- Новые репозитории (open / clone / init) попадают в активный воркспейс; перенос — через контекстное меню карточки «Move to @…».

- **Папка воркспейса и автосканирование**: у воркспейса можно задать корневую папку и глубину (1–6). Входы: кнопка «Choose folder to scan…» рядом с заголовком Repositories на стартовом экране, пункт «Choose root folder to scan…» в меню `@workspace`, диалог Edit workspace. В Prong.app открывается системный выбор папки и скан стартует сразу; в веб-версии путь вводится в диалоге. Движок (`POST /api/scan`) обходит дерево, пропуская `node_modules`, `build`, `.git` и т. п., находит каталоги с `.git`; внутрь найденного репозитория не заходит, поэтому сабмодули и вложенные чекауты не регистрируются и добавляет найденные репозитории в воркспейс. Сканирование запускается при старте, при сохранении папки и по кнопке Rescan на стартовом экране; воркспейсы и их папки хранятся в `~/.prong/workspaces.json`.

### 3.1 Welcome / список репозиториев

- Список недавних репозиториев с путём, текущей веткой, числом изменений; поиск; закрепление.
- Кнопки: Open (диалог выбора папки), Clone, Init.
- Клонирование: URL или выбор из списка репозиториев подключённого GitHub-аккаунта; целевая папка; имя; чекбокс «recursive submodules»; прогресс с логом `git clone --progress`.
- Dropzone: папку можно перетащить в окно.

### 3.2 Аккаунты и ключи (Preferences → Accounts / SSH)

- **GitHub**: вход по Device Flow (показываем код, открываем github.com/login/device, поллим токен); для GitHub Enterprise — host + PAT. После входа: аватар, логин, список организаций. Токен используется как HTTPS-credential (через `GIT_ASKPASS`-мост в нашем модуле) и для списка репозиториев при клонировании.
- **SSH-ключи**: список ключей из `~/.ssh` (`id_*`, `*.pub`), генерация новой пары (`ssh-keygen -t ed25519`), копирование публичного ключа, кнопка «Добавить в GitHub» (API `user/keys`), добавление в ssh-agent, проверка соединения (`ssh -T git@github.com`). Пароль ключа — в Keychain.
- Per-repo переопределение identity (user.name / user.email) и выбор ключа (`core.sshCommand`).

### 3.3 Changes (локальные изменения)

- Две секции: **Unstaged** и **Staged**, каждая — список файлов с иконкой статуса (M/A/D/R/C/U/?), путём, кнопками Stage/Unstage на hover, контекстное меню (Discard, Ignore, Open, Reveal, Copy path).
- Кнопки «Stage all», «Unstage all», «Discard all» с подтверждением.
- Дифф выбранного файла справа: хунки с действиями «Stage hunk / Discard hunk», выбор отдельных строк (shift-click) → stage lines.
- Внизу: поле сообщения коммита (summary + description, счётчик 50/72), чекбокс **Amend**, подпись GPG/SSH (если настроена), кнопка **Commit** (⌘⏎), выпадашка «Commit & Push».
- Конфликты (U): файл помечен, дифф показывает три панели (ours/theirs/result) с кнопками «Take ours / theirs / both», «Mark resolved».

### 3.4 All Commits (граф)

- Граф слева (SVG): линии ветвей с цветом по «дорожке», точки коммитов, merge-точки крупнее, HEAD — кольцо. Виртуализированный список, окно рендера ±50 строк, граф строится инкрементально (`git log --topo-order --parents`).
- Строка: метки (локальные ветки — синие, remote — серые с иконкой облака, теги — жёлтые, HEAD — выделен), сообщение (первая строка), автор с аватаром, относительная дата, короткий хеш.
- Строка WIP «Uncommitted changes (N)» сверху, если есть изменения; клик → Changes.
- **Рендер графа**: один SVG-слой на весь видимый диапазон строк (а не SVG на строку), поэтому линии не рвутся на границах строк; у каждого узла рисуется входящий отрезок сверху, если дорожка уже «ждала» этот коммит. В production SVG строится для окна ±100 строк и переиспользуется при скролле.
- **Сворачивание мержей (как в Fork)**: у merge-коммита узел с «−»; клик (или ←/→ на выбранном коммите, или двойной клик по строке) прячет коммиты боковой ветки — всё достижимое из второго родителя, но не из первого. Свёрнутый мерж рисуется квадратом с «+», пунктирным «хвостом» и бейджем «+N hidden»; граф перестраивается с переподключением родителей к ближайшему видимому предку. «Collapse all / Expand all» — в панели фильтра и в контекстном меню.
- **Фильтр веток**: кнопка «Branches ▾» над графом — режимы All / Current / Selected, чекбоксы по локальным, remote-веткам и тегам, «Hide remote branches». Из контекстного меню ветки в сайдбаре: «Show only this branch», «Hide from graph», «Show all». Скрытые ветки в сайдбаре притушены. Видимые коммиты = объединение достижимых из выбранных ссылок.
- Поиск: по сообщению / автору / хешу / файлу (`git log -S`), фильтр «только текущая ветка / все ветки».
- Контекстное меню коммита: Checkout, Create branch here, Create tag, Cherry-pick, Revert, Reset (soft/mixed/hard), Rebase current branch onto this, Interactive rebase from here, Copy SHA, Copy message.
- Drag & drop ветки на другую ветку в графе = merge / rebase (как в Fork, с подтверждением).

### 3.5 Details / Diff

- Заголовок коммита: subject, body (моноширинный блок), автор/коммитер с датами, SHA (копируется), родители (ссылки), метки.
- Файлы: переключатель List/Tree, счётчик +/−, фильтр по имени.
- Дифф: unified / split, номера строк, подсветка синтаксиса (prism-подобный токенайзер в TS, без WebView), word-diff внутри изменённых строк, сворачивание неизменённых областей, «Expand context ±10», переход между хунками (F7/F8).
- Типы контента:
  - текст — дифф;
  - картинки (png/jpg/gif/webp/svg…) — баннер «new file / deleted / same content / modified» с размерами; режимы side by side, swipe (разделитель следует за курсором), onion skin и difference показываются, только когда есть обе версии, difference — только при равных пиксельных размерах; общий зум и пан для всех панелей: перетаскивание и прокрутка двигают, pinch / ⌘+колесо масштабируют вокруг курсора, двойной клик — 1:1, выше 2× пиксели чёткие; координаты пикселя под курсором;
  - аудио — плееры до/после, длительность, волна с перемоткой кликом, связанное воспроизведение; видео — плееры, длительность и разрешение, разница; неподдерживаемый формат объясняется и открывается в приложении по умолчанию;
  - бинарники — «Binary file changed, N → M (±Δ)» по данным движка, Open / Reveal;
  - rename — путь `old → new`, similarity %;
  - submodule — старый/новый SHA;
  - большие файлы (> 1 MB дифф) — предупреждение и кнопка «Load anyway».
- File history: правый клик по файлу → «History», открывает граф с фильтром по пути; Blame — построчно, автор/дата в желобе, клик по строке → коммит.

### 3.6 Branches / Remotes / Tags / Stashes

- Сайдбар группирует ветки по `/` в раскрываемое дерево; у текущей — точка и ahead/behind; у remote-ветки — иконка облака. Двойной клик — checkout. Контекст: Checkout, Merge into current, Rebase current onto, Rename, Delete (с remote), Push, Pull, Set upstream, Copy name.
- Remotes: список с URL, Add/Edit/Remove, Fetch, Prune.
- Tags: список, Create (lightweight/annotated), Push tag, Delete.
- Stashes: список с сообщением и датой; клик показывает содержимое как коммит; Apply / Pop / Drop; создание стэша из Changes (с чекбоксом «keep staged» и «include untracked»).

### 3.7 Операции и диалоги

| Операция | UI | Команда |
|----------|----|---------|
| Fetch | кнопка / ⌘⇧F, выбор remote, prune | `git fetch --prune` |
| Pull | кнопка, стратегия merge / rebase / ff-only | `git pull [--rebase]` |
| Push | кнопка, выбор remote и ветки, force-with-lease, push tags | `git push` |
| Commit | панель Changes | `git commit` |
| Merge | диалог: источник, no-ff, squash | `git merge` |
| Rebase | диалог: onto, interactive-чекбокс | `git rebase` |
| Interactive rebase | список коммитов с действиями pick/reword/edit/squash/fixup/drop, перетаскивание порядка | `git rebase -i` с нашим `GIT_SEQUENCE_EDITOR` |
| Cherry-pick / Revert | контекст коммита | `git cherry-pick` / `git revert` |
| Reset | диалог soft/mixed/hard | `git reset` |
| Checkout | двойной клик / диалог | `git checkout` / `switch` |
| Stash | кнопка | `git stash push` |
| Conflicts | панель слияния | `git checkout --ours/--theirs`, `git add` |
| Submodules | статус в Changes, Update/Init | `git submodule` |
| Terminal | кнопка «Open in Terminal» | системный терминал в cwd |

Длительные операции показываются в статус-баре с прогрессом и кнопкой Cancel (SIGTERM процессу). Ошибки git — в тостах с полным stderr по клику.

### 3.8 Клавиатура

⌘T новая вкладка, ⌘W закрыть, ⌘1/2 переключить Changes/All Commits, ⌘⏎ commit, ⌘⇧F fetch, ⌘⇧P push, ⌘⇧L pull, ⌘F поиск, ⌘K палитра команд, ⌘, настройки, F7/F8 — следующий/предыдущий хунк, Space — stage/unstage выделенного файла.

## 4. Визуальный стиль и анимации

Выбрано направление **01 Monospace Terminal** (см. `DESIGN-STYLES.md`). Реализовано в `src/theme/index.ts`, 2026-10-19.

- **Шрифт**: JetBrains Mono везде (UI, метки, хеши, дифф) через `@expo-google-fonts/jetbrains-mono`; веса 400/500/600/700 как отдельные семейства, подбираются `theme.fontFor(weight)`. Базовый размер 12 px, строки списков 22 px.
- **Палитра (тёмная)**: фон #0f1113, панели #131619/#171b1f, поднятое #1f2429, рамки #262c33/#343c45, текст #d9dee3/#8a949e/#596470, акцент янтарный #e8b23b (режим, текущая ветка, выделение), добавления #6ad48c, удаления #ff7369, инфо #5fcad8, теги #d7a1ff. Дорожки графа — ANSI-подобная шестёрка: янтарный, циан, сиреневый, зелёный, синий, оранжевый. Светлая тема зеркальная на холодной бумаге #f3f3f0 с тёмным янтарём #a86f08.
- **Форма**: радиус 0 везде, границы 1 px, без теней внутри окна. Метки и кнопки — uppercase с трекингом 0.8 px. Чипы веток в `[скобках]`, теги в `<угловых>`, текущая ветка — залитый янтарный блок.
- **Выделение**: в списке коммитов — инверсия (янтарный блок, тёмный текст, как курсор); в сайдбаре и списках файлов — мягкая подсветка `raised`. Активные пункты и вкладки помечаются `▸`.
- **Тулбар** 36 px в одну строку: иконка 13 px + uppercase-подпись, счётчики квадратными бейджами. Поиск начинается с `/`, палитра команд с `:`. Статус-бар 22 px со «штампом режима» слева: NORMAL / MERGE / BUSY.
- **Граф**: линии 1.5 px, узлы — ромбы 7 px, HEAD — пустой ромб, мерж — квадрат с «−», свёрнутый мерж — залитый квадрат с «+» и пунктирным хвостом.
- **Всплывающие элементы (диалоги, контекстные меню, поповеры, тосты)** — матовое стекло без обводки: `Glass` в `src/ui/primitives.tsx`: полупрозрачный фон rgba(22,25,29,.84), мягкая тень, на web — `backdrop-filter: blur(34px) saturate(.7) contrast(.92)` через атрибут `data-glass` (размытие и приглушение цвета под попапом дают «матовость»); в нативной сборке — `expo-blur`/NSVisualEffectView. Подложка диалога только затемняется.
- **Цветовые схемы** (одна система, пять палитр, `SCHEMES` / `THEMES` в `src/theme`): Amber (графит + янтарь, по умолчанию), Phosphor (чёрный + фосфорный зелёный), Ice (сланец + циан), Solar (глубокий бирюзовый + солнечный жёлтый, по мотивам Solarized), Paper (светлая бумага + тёмный янтарь). Выбор: Preferences → General (карточки-превью), кнопка схемы в тулбаре, палитра команд. Схема задаёт акцент, выделение, дорожки графа, цвета диффа и стекла.
- **Масштаб интерфейса**: 80 / 90 / 100 / 110 / 125 / 150 %, ⌘+ / ⌘− / ⌘0 и Preferences → General. На web применяется CSS `zoom` к корневому контейнеру приложения, которому явно задаётся размер `окно / масштаб`, поэтому раскладка всегда вписывается в окно (статус-бар не уезжает). Координаты мыши и размеры окна внутри переводятся в «layout px» через `toLayout()` / `useViewport()` (`src/ui/primitives.tsx`); все расчёты высот панелей, меню и сплиттеров идут через них. На узких окнах колонки списка коммитов и статус-бар ужимаются, палитра команд в тулбаре скрывается. В нативных сборках — тот же `uiScale` множителем размеров темы (этап 2).
- **Ресайз и перетаскивание попапов**: все диалоги (`Modal`) тянутся за правый нижний угол (`ResizeGrip`) и перетаскиваются за заголовок (`DragHandle`); при заданной высоте тело диалога прокручивается. Поповеры (фильтр веток, воркспейсы) тоже тянутся за угол. Контекстные меню не ресайзятся. Все всплывающие слои — один компонент `Glass` (одинаковая матовость и размытие), глобальные кнопки схемы / аккаунтов / настроек живут в полосе вкладок и доступны со стартового экрана; меню открываются у своей кнопки (якорь через `onPressAt`).
- **Движение**: множитель `theme.motion = 0.5`; переходы 60–80 ms без сдвига, только fade; единственная «живая» анимация — мигающий блочный курсор (`Cursor`) и спиннер операций.

## 4.1 Агент и самоизменяемое приложение

**Концепция.** Prong поставляется вместе со своими исходниками и собирает интерфейс из них на лету, как в режиме разработки. Локальный ИИ-агент получает текстовые команды двух видов: по работе с репозиторием (ветки, коммиты, rebase, push…) и по изменению самого приложения (убрать лишнее, добавить недостающее, перекроить экран). Все изменения интерфейса версионируются: любое можно откатить, вернуться на предыдущую версию или сбросить всё к заводской сборке.

**Агент по умолчанию** — Anthropic через локальный Claude Code на машине пользователя: Prong запускает `claude -p` с рабочей директорией репозитория (для команд git) или папки исходников приложения (для изменений UI), с набором инструментов «читать/писать файлы, запускать git, typecheck, bundle». Альтернативы в настройках: прямой Anthropic API, любой OpenAI-совместимый endpoint. Модель, путь к бинарю и папке исходников настраиваются; есть проверка соединения (`claude --version`).

**Как это устроено в production (этап 2–3):**
- Исходники приложения лежат в `~/Library/Application Support/Prong/src` и являются git-репозиторием с тегом `factory/<версия>`; встроенный bundler (Metro / Hermes) собирает их при старте и по hot reload после изменения. Заводская сборка вшита в бинарь как запасной вариант.
- Каждая принятая правка агента = коммит в этом репозитории (сообщение = команда пользователя). Журнал версий в панели = `git log`; «Revert» = `git revert` одной правки, «Roll back here» = checkout состояния на этой версии с сохранением журнала, «Reset to factory» = checkout тега. Поскольку Prong сам git-клиент, папку исходников можно открыть как обычный репозиторий и смотреть диффы агента штатными средствами.
- Безопасность: агент ограничен папкой исходников и текущим репозиторием; перед применением можно включить показ диффа и подтверждение; после правки прогоняются typecheck и сборка, при ошибке автоматический откат; если приложение не поднялось после правки, оно стартует в safe mode из заводских исходников и предлагает откат.
- Команды по репозиторию выполняются через тот же `GitClient`, что и UI, и показываются в чате как выполненные действия (с командами git).

**Как правка доходит до окна (2026-10-22).** Перед прогоном в режиме приложения движок запоминает, какие файлы исходников уже изменены. После прогона изменённые агентом файлы становятся версией: коммитом в собственном git исходников, а если папка не репозиторий (как `prong` внутри `zenkovich.space`), в теневом репозитории `~/.prong/app-sources/<hash>.git` с этой папкой как рабочим деревом; в саму папку ничего не пишется. Затем движок собирает интерфейс (`expo export` своим Node) в `~/.prong/ui/builds/<stamp>`, переключает раздачу на новую сборку и рассылает `ui-updated`: окна сохраняют чат, уведомления и вкладки и перезагружаются. Сборка с ошибкой не раздаётся, правка откатывается (настройка автоотката). Откат и повторное применение версии — `git revert` и снова сборка. Заводская сборка внутри приложения новее агентской — раздаётся она (её собрали из тех же исходников позже). За dev-сервером Metro пересборка не нужна. Правило «задача для другой цели» каждой цели сообщается только про другую; если модель всё же назвала свою цель, запрос повторяется один раз, затем честно сообщается, что ничего не сделано.

**Строка агента (2026-10-21).** Кнопка `agent` в верхней полосе по клику или ⌘J разворачивается в строку ввода с целью auto / repo / app; Esc сворачивает. Пока агент работает, в строке короткий статус по событиям Claude Code («Reading store.ts», «Type-checking», «Running git log…»), секундомер, кнопка ■ (движок убивает группу процессов Claude Code) и ⤢. По завершении под строкой остаётся карточка: итог, сводка действий («2 files edited · 1 read · commit …»), время и стоимость, Open chat / Reply / Revert версии; закрывается только вручную. Если чат открыт, карточка не нужна. ⤢ или ⌘⇧J открывают полное окно.

**Панель.** Полное окно агента — правая панель с ресайзом: вкладки Chat (команды, цель auto / repo / app, подсказки, транскрипт с выполненными действиями и чипом версии), Changes (журнал: v0 factory, v1…, статус applied / reverted / current, детали с промптом, файлами и диффом, Revert / Re-apply / Roll back here / Reset to factory), Settings (провайдер, модель, бинарь, папка исходников, dev-сервер, подтверждение и автооткат). Кнопка показывает число применённых версий.

**Прототип.** Агент мок (`src/agent/mockAgent.ts`): распознаёт набор команд на русском и английском. Команды репозитория исполняются через мок-стор, изменения интерфейса превращаются в патч «модификаторов приложения» (`AppMods`: скрыть колонку автора, компактный тулбар, убрать/добавить кнопки, схема, абсолютные даты, толщина графа, ширина сайдбара, высота строк, штамп режима) с правдоподобным списком файлов и фрагментом диффа. Эффективные модификаторы = заводские + все применённые версии по порядку, компоненты читают их через `useMods()`.

### Клиент на большой истории (2026-10-22, `~/work/homescapes`)

Профиль всех сценариев — `node tools/profile.mjs <repo>` (см. `docs/PERFORMANCE.md`). Что было узким местом и как устроено теперь:

- **Граф.** У проекта с тысячами веток одновременно открыто до 120 дорожек; каждая строка рисовала линию на каждую, хотя видно 12 колонок (дальние рисовались друг на друге): 138 тыс. SVG-элементов на 1 800 коммитов, 850 тыс. на 8 000. `layoutGraph(list, cols)` оставляет одну запись на колонку.
- **Список истории виртуализирован** (`src/ui/virtual.ts`): рисуются видимые строки и полоса графа под ними, окно сдвигается шагами по 10 строк. Раскладка, сворачивание мержей и «серые» коммиты кэшируются по объекту списка — возврат в историю из Changes или с другой вкладки не пересчитывает 19 тыс. коммитов.
- **Клик по глубокой ветке** — один потоковый `git log` от загруженного до коммита и ещё 200 (`logUntil`), вместо страниц по 300 с перерисовкой после каждой; до 60 000 коммитов вглубь, дальше — уведомление «Too deep in the history» с подсказкой про воронку.
- **Обновление** не сбрасывает дочитанную историю: при тех же ссылках список остаётся, при изменившихся — перечитывается та же глубина одним вызовом.
- **Коммит с сотнями файлов** (мерж на 55 тыс. файлов давал патч 930 МБ — больше, чем вмещает строка JS) приходит списком (`git show --raw`, 0.2–0.5 с), дифф файла читается при выборе (`commitFileDiff`). Вывод git ограничен по объёму (`maxBytes`), при превышении — список вместо патча, у одного файла — пометка «Diff cut short».
- **Список файлов** (коммит, stash, Changes) виртуализирован, дерево строится через словари (было квадратичным).
- **Сворачивание мержей** — обход в порядке истории от обеих сторон мержа до базы (стоимость — длина влитой ветки, а не всей истории), на типизированных массивах; «Collapse all» не обходит мержи, уже скрытые внутри свёрнутых.
- **Сайдбар.** Строки веток и тегов мемоизированы и подписаны только на свои значения (`useRepoValue`): выбор коммита больше не перерисовывает тысячи строк; текущая ветка для меню ищется при открытии меню.
- **История файла** без `--follow` (тот обходит всю историю, 9 с): обычный `git log -- path` с фильтрами commit-graph, а переименования прослеживаются по одному шагу (`diff -M` самого старого коммита). Из деталей коммита история идёт от этого коммита.
- **Сабмодули**: вместо `git submodule status` (describe по очереди, 1.3 с на 20) — коммиты из индекса и параллельные `rev-parse`/`describe` (0.2 с).

## 4.4 Медиа, иконки, вкладки, безопасность движка (2026-10-21)

- **Почему превью падали.** Виды не-текстовых изменений были написаны под мок-данные и читали поля, которых настоящий дифф не содержит: размеры бинарника (`file.binary!`), картинки коммита. Теперь всё про стороны изменения отдаёт движок (`mediaSides`: есть ли сторона, размер, oid), содержимое идёт отдельным запросом `GET /api/blob?repo&rev&file` с Range (WebKit играет видео только с 206), blob извлекается потоково в кэш по oid. Каждое превью обёрнуто в собственную границу ошибок: сбой показывает причину на месте, остальной интерфейс не трогает.
- **Иконки файлов.** Material Icon Theme (MIT): таблица соответствий в бандле, SVG статикой из `public/file-icons`; порядок как в VS Code (имя файла, самое длинное составное расширение, светлые варианты). Неизвестные расширения — иконка ОС через `/api/fileicon`: macOS (NSWorkspace через JXA, пакетно), Windows (ExtractAssociatedIcon), Linux (gio / xdg-mime → тема иконок freedesktop); кэш на диске.
- **Вкладки.** Сабмодули (любой открытый репозиторий внутри другого открытого) идут сразу за родителем под-вкладками с относительным путём и общей линией группы; у неактивной группы они свёрнуты в «+N» с меню. Ширина как у вкладок браузера: естественная при наличии места, сначала ужимается самая широкая, не ниже минимума, дальше прокрутка с активной вкладкой в зоне видимости; у неактивных вкладок кнопка закрытия появляется поверх текста при наведении и не съедает ширину.
- **Горячие клавиши при вводе.** Текстовые поля react-native-web гасят всплытие keydown, поэтому глобальные сочетания не работали с фокусом в поле. Все обработчики клавиатуры слушают в фазе перехвата; клавиши без модификаторов проверяют, не печатает ли пользователь.
- **Безопасность движка.** Раньше движок отвечал на CORS `*`: любая страница в браузере могла управлять git, файлами и агентом через 127.0.0.1. Теперь Host должен быть loopback (защита от DNS rebinding), Origin — сам движок, dev-серверы Expo или `PRONG_ALLOWED_ORIGINS`; cross-site встраивание без разрешённого Referer отклоняется; CORS — точное эхо разрешённого origin.

- **Сайдбар.** Разделитель после Changes / All Commits, фильтр по веткам, remote, тегам и сабмодулям (группы и папки раскрываются, пустые группы скрыты). Кнопки «+» и действия в заголовках групп всегда на месте (бледные до наведения): раньше они появлялись только при наведении на строку и исчезали, когда курсор переходил на саму кнопку. Сабмодули деревом по папкам или списком, дерево по умолчанию, выбор запоминается.
- **Удаление веток.** Удалённая ветка удаляется `git push <remote> --delete`; если её на сервере уже нет — удаляется устаревшая ссылка. Раньше движок сначала пытался удалить несуществующую локальную ветку, падал, и список не менялся. «Delete (local + remote)» удаляет и ветку, которую локальная отслеживает.
- **Changes.** Поле сообщения коммита под диффом (как в Fork). У кнопки коммита меню «Commit» / «Commit and push»; выбор запоминается, ⌘⏎ следует ему; подпись автора берётся из git.
- **История.** Под графом — описание коммита во всю ширину, ниже файлы (дерево или список) слева и дифф справа. Метки как в Fork: локальная ветка и её ветка на origin на одном коммите — одна метка с облаком, удалённые без локальной — своя метка с облаком; коммиты вне текущей ветки серые; HEAD жирным.
- **Подсветка** во всех текстовых файлах: языковые определения по имени и расширению (JS/TS, JSON, Python, Go, Rust, C/C++/ObjC, Java/Kotlin, C#, Swift, PHP, Ruby, shell, SQL, Lua, Dart, Make, Docker, разметка, CSS, Markdown, YAML, INI/TOML) и обобщённый режим для остальных.
- **Стейджинг строк.** Клик по изменённой строке выбирает её, shift-клик — диапазон; в заголовке ханка «Stage / Discard / Unstage N lines». Клиент строит частичный ханк, движок применяет его теми же `git apply`, что и целый ханк; создание или удаление файла в патче только для целого файла.
- **Группы вкладок.** Родитель и его сабмодули в одной рамке, у вкладок сабмодулей стрелка к родителю; группа не сворачивается сама, кнопка в конце рамки сворачивает её в «+N» (как группы вкладок Chrome).
- **Шапка.** Кнопка воркспейса без рамки, меню — список воркспейсов, «New workspace…», «settings…». Кнопки схемы нет: схема в настройках и палитре.
- **Журнал версий агента.** В теневом журнале ручные правки исходников фиксируются коммитом «Manual changes» перед прогоном агента и перед откатом, чтобы `git revert` версий не упирался в них.

## 4.6 Клик по ветке, фильтр как в Fork, размеры поля коммита (2026-10-22)

- **Клик по ветке или тегу** в сайдбаре выделяет её коммит и прокручивает историю так, чтобы строка была в верхней трети списка. Если коммит старше загруженного, клиент дочитывает лог страницами по 300 (до 25 страниц), в том числе отфильтрованный. Коммит внутри свёрнутого мержа раскрывает мержи. Если коммит скрыт фильтром или старше прочитанного, в строке уведомлений об этом сказано. Двойной клик, как и раньше, переключает ветку.
- **Воронка** справа от каждой ветки и тега: видна при наведении, у веток в фильтре горит постоянно. Первый клик показывает только эту ветку, следующие воронки добавляют ветки, повторный клик убирает; когда убрана последняя, видны все ветки. Над историей полоса «Showing only» с плашками веток (× убирает одну) и «Clear filter». В контекстном меню ветки: «Show only this branch», «Add to / Remove from the filter», «Clear the branch filter».
- **Поле коммита** растягивается разделителем над ним (124–640 px), рост уходит в поле описания. Шеврон справа от счётчика сворачивает описание: остаётся строка заголовка, первая строка описания и кнопки. Высота и свёрнутость запоминаются.
- **Описание коммита в истории** растягивается разделителем под ним (64–480 px). Шеврон в правом верхнем углу сворачивает его в одну строку: заголовок, автор, короткий хеш. Высота и свёрнутость запоминаются.

## 4.7 Ошибки (2026-10-22)

- Любая ошибка открывает **окно ошибки** поверх всего, в том числе поверх другого диалога: что не удалось, подсказка, что делать (правила в `src/state/errorHints.ts`: локальные изменения мешают checkout, push отклонён, нет SSH-ключа или учётных данных, конфликты, `index.lock`, недопустимое имя ветки, сеть, движок не отвечает), и вывод git целиком — моноширинно, с выделением и прокруткой. Кнопки: «‹ Newer / Older ›» по ошибкам сессии, «Copy», «Clear log», «Close»; Enter и Esc закрывают только это окно, клавиши не доходят до того, что под ним.
- Журнал сессии — 50 последних ошибок; та же ошибка в течение минуты увеличивает счётчик «×N».
- В строке состояния — первая строка ошибки, обрезанная по ширине, со ссылкой «details»: клик открывает окно (раньше строка просто исчезала). Значок ⚠ с числом открывает журнал в любой момент.
- Движок и клиент больше не обрезают сообщения git до двух строк; у длинных операций (fetch, push, clone) в окно попадает и хвост их вывода, у исключений — стек.
- Сообщение об успехе операции показывается только при успехе: раньше после ошибки checkout появлялось зелёное «Checked out …».

## 4.8 Переход к сабмодулю из изменений коммита (2026-10-22)

- У изменения сабмодуля в коммите (и в Changes): оба указателя кликабельны, кнопка «Go to <sha> in <name>», список коммитов сабмодуля, которые принёс сдвиг указателя, а если указатель ушёл назад — оставленных; клик по любому открывает вкладку сабмодуля (в группе с родителем) с этим коммитом, глубокий дочитывается одним вызовом.
- В списке файлов коммита двойной клик по строке сабмодуля и пункт меню «Open submodule at <sha>» делают то же.
- Если в клоне сабмодуля нужного коммита нет, вкладка открывается, а окно ошибки подсказывает fetch или «Update to index»; не склонированный сабмодуль показан с подсказкой, кнопка перехода неактивна.

## 4.9 Вкладки и фильтры между запусками, подключение к удалённым (2026-10-22)

- **Сессия.** Движок хранит `session.json`: активный воркспейс, вкладки каждого воркспейса и активную вкладку, фильтр веток каждого репозитория. Сохраняется через полсекунды после изменения, при запуске возвращается: вкладки исчезнувших репозиториев отбрасываются, остальные грузятся при первом показе, каждая со своим фильтром; ветки, удалённые с прошлого раза, из фильтра выбрасываются до обращения к git. Локальное хранилище окна теперь держит только чат агента между перезагрузками интерфейса.
- **Подключение репозитория** (меню More → «Connection», ключ в заголовке Remotes, пункт меню remote, кнопка в окне ошибки входа): системное по умолчанию, SSH-ключ из `~/.ssh` или аккаунт Prong. Хранится в записи репозитория у движка; сабмодули и всё внутри папки репозитория наследуют настройку ближайшего родителя, пока у них нет своей; диалог сабмодуля показывает, от кого она унаследована, и позволяет переопределить.
- Как применяется: все сетевые команды (fetch, pull, push, теги, удаление удалённых веток, prune, submodule update) идут через `Repo.net()`. SSH-ключ — `GIT_SSH_COMMAND` с `-i <key> -o IdentitiesOnly=yes -o BatchMode=yes` (ключ из агента тоже подходит, если в агенте он есть). Аккаунт — токен из Keychain через помощник учётных данных, который отвечает только хосту аккаунта; токен идёт в окружении, не в командной строке; SSH-адреса этого хоста на время команды переписываются в HTTPS. Клон сабмодуля при `submodule update` получает то же через окружение и `-c`.
- «Test connection» проверяет выбор до сохранения (`git ls-remote <remote> HEAD`, только чтение). Аккаунт, у которого в организациях есть владелец удалённого репозитория, помечен «member of <org>».
- Ключ или аккаунт, которых больше нет, дают понятную ошибку, а не тихий откат к умолчанию.

## 4.10 Список репозиториев у «+», ветки пачкой, двойной клик (2026-10-23)

- «+» в строке вкладок и ⌘T открывают список репозиториев воркспейса, как на домашней странице (закреплённые, затем недавние), поверх окна: набор сужает, стрелки и Enter или клик открывают во вкладке, уже открытые помечены; внизу «Open folder…», «Clone…» и переход на домашнюю страницу.
- Ветки (локальные и удалённые) выбираются пачкой: ⌘-клик добавляет и снимает, Shift-клик — отрезок в порядке сайдбара. Внизу сайдбара полоса «N selected»: «Show only» (фильтр истории по ним), «Push» (одним push с upstream), «Delete…» (диалог со списком; «also delete their branches on the remote», «also unmerged»). То же — в контекстном меню выбранной ветки, плюс «Copy names». Что git не сделал, попадает в окно ошибки с причиной для каждой ветки; Esc снимает выбор.
- Двойной клик — второе нажатие того же элемента, которое система считает вторым щелчком (счётчик щелчков у mousedown, `detail`), без других нажатий между ними; 450 мс — только запасной путь без мыши. Время между обработчиками не учитывается: первый щелчок по ветке большого репозитория может занять страницу на секунду, и двойной клик всё равно засчитывается. В списке веток переключает на ветку; на коммите — на его ветку, при нескольких — меню выбора в месте клика; мерж без веток сворачивается.

## 4.11 Переключение как в Fork, очередь действий (2026-10-23)

- Удалённая ветка при переключении — это её локальная: та, что её отслеживает, иначе одноимённая, иначе новая с отслеживанием (`switch -c имя remote/имя`, для любого remote, не только origin). Уже текущая — «Already on …».
- Если git отказывается переключать из-за локальных изменений (отслеживаемых или неотслеживаемых), в окне ошибки есть кнопка «Stash, switch and reapply»: stash с неотслеживаемыми, переключение, `stash pop`. Конфликт при возврате — сообщение, изменения в рабочей копии с маркерами и в stash до ручного удаления.
- Движок ставит всё, что меняет репозиторий, в очередь этого репозитория (`server/src/queue.ts`): действия идут по одному в порядке запросов (короткие операции и долгие — fetch, pull, push, обновление сабмодулей). Перед запуском очередь ждёт, пока нет `index.lock`, `HEAD.lock`, `config.lock`, `packed-refs.lock` (их держит другой git: терминал, IDE, фоновый `git status`); если git всё же упал на блокировке, действие повторяется (до 10 раз). Чтения в очередь не попадают и не ждут. Через 30 минут ожидания действие завершается ошибкой.
- Состояние очередей — SSE-событие `queue` (`repo`, `items`: queued / waiting-lock / running, файл блокировки и время его последнего изменения) и `GET /api/queue` для только что открытого окна; `POST /api/queue/cancel` убирает ещё не начатое действие (запрос отвечает «Cancelled», интерфейс пишет «cancelled», не ошибку).
- В строке состояния — индикатор очереди активного репозитория: «Waiting for index.lock · Checkout …» или «Checkout …» с числом ждущих, если что-то ждёт или действие идёт дольше 0,7 с (долгие операции с прогрессом не дублируются). По клику — список над строкой: что идёт, что ждёт, крестик отмены; у блокировки, не менявшейся больше минуты, — «Delete index.lock…» с подтверждением (движок удаляет только файлы из списка выше и отказывает, если файл менялся меньше минуты назад).

## 4.12 Обновление при возврате, удалённые ветки клона на одну ветку, «Ask AI» (2026-10-23)

- Как в Fork: при возврате в окно (focus, видимость, сигнал оболочки macOS `prong-activate` из `applicationDidBecomeActive`) и при переходе на вкладку репозиторий перечитывается — коммиты, ветки и изменения, сделанные в терминале или IDE, появляются без ⌘R. Не чаще раза в 2 с на репозиторий и не поверх идущего чтения; открытие вкладки читает само. Удалённые ветки по-прежнему обновляет только fetch.
- Клон на одну ветку (сабмодуль вроде vso-engine: `+refs/heads/master:…`) получает именной refspec при публикации ветки из Prong. Когда сервер удаляет такую ветку, git валит каждый fetch и pull: «couldn't find remote ref refs/heads/…». Теперь fetch и pull проверяют её `ls-remote` и, если её нет, убирают refspec и устаревшую `refs/remotes/…` (как `--prune` для остальных), повторяют команду и пишут в лог «Deleted on the remote, no longer fetched: …». Локальная ветка остаётся (upstream gone). Remote с единственным refspec не трогается; для него и для pull с исчезнувшим upstream — подсказки в окне ошибки.
- «Ask AI» в окне ошибки, в неудачной проверке подключения и на экранах сбоя панели: ошибка уходит агенту (Claude Code) с заголовком, выводом git или стеком (длинный — начало и конец), репозиторием и текущей веткой, и с правилами (сначала причина; исправлять, только если безопасно — без потери коммитов и изменений, без force-push; иначе предложить команды; в конце — что было и что сделано). Ошибка git — режим repo в том репозитории, где случилась (запоминается в записи журнала); «Unexpected error» и сбой панели — режим app, в исходниках Prong. Чат открывается на запуске; в чате короткий вопрос, подробности видит только агент.

Следующее сообщение в той же цели и папке запускается с `--resume` — «да, сделай» после предложения агент понимает. Ответ без слов про git или интерфейс («да», «почему?») в режиме auto идёт туда же, где был разговор, в тот же репозиторий, даже с другой вкладки. Чат и карточки агента рисуют его сами (`src/components/markdownSyntax.ts` — разбор, `Markdown.tsx` — вид): заголовки, списки (вложенные, нумерованные), блоки кода с подписью языка и кнопкой Copy (строки переносятся), таблицы с прокруткой вбок, цитаты, `код`, жирный, курсив, ссылки и голые URL открываются в браузере.

- Вопрос «Ask AI» в чате — Markdown: просьба, **заголовок ошибки**, `репозиторий` · ветка, начало вывода git в блоке кода (12 строк); агенту дополнительно — полный вывод, правила и вид ответа («### Причина», «### Что сделано», «### Что сделать вам»).

## 4.14 Fetch, Pull, Push как в Fork (2026-10-23)

- Кнопки панели открывают окна с параметрами (как в Fork, Enter — выполнить); стрелка рядом — быстрые действия без окна: «Fetch all remotes now» / «Fetch <remote> now», «Pull … now» и варианты merge / rebase / fast-forward, «Push <ветка> → <remote/ветка> now», «Push with all tags». Палитра: «Fetch…», «Fetch all remotes now», «Pull…», «Push…».
- Fetch: remote — все или один (выпадающий список с адресами); «Prune: remove remote branches deleted on the server»; «Fetch all tags» (`--tags`; git не удаляет теги, полученные так, поэтому локальные теги переживают prune). Ниже — прежние блоки про клон на одну ветку и неполную историю.
- Pull: remote и ветка на нём (по умолчанию upstream текущей; список с фильтром, upstream первым), «Into» — текущая ветка; под ней — что придёт (N новых коммитов, неотправленные локальные) или что это не upstream и он останется прежним; режим Merge / Rebase / Fast-forward only (запоминается как pull mode из Preferences, им же пользуется быстрый pull); «Stash and reapply local changes» (`--autostash`) с подсказкой о числе локальных изменений. Отсоединённый HEAD — объяснение вместо полей.
- Push: любая локальная ветка (текущая первой), «To» — remote / имя ветки на нём (по умолчанию та, что отслеживается, иначе то же имя; поле свободное, ▾ — список существующих); под ним — что произойдёт (N коммитов к отправке, «на сервере есть коммиты, которых нет здесь», «создаст …», «обновит …, которую ветка не отслеживает»); «Track <remote/ветка>» (по умолчанию, если upstream нет), «Push all tags», «Force push (--force-with-lease)» — кнопка и иконка красные, с предупреждением. Пункт «Push» в меню ветки сайдбара пушит её (любую, не только текущую) или открывает окно.
- Выбор remote в Fetch, prune, теги, autostash и теги push запоминаются (`syncPrefs` в настройках интерфейса). Движок: `fetch {remote, prune, tags}`, `pull {strategy, remote, branch, autostash, tags}`, `push {remote, branch, remoteBranch, force, tags, setUpstream}` — имена remote и веток проверяются.
- Выпадающие списки окон (`Select` → `PickerHost`) рисуются над окном, не обрезаются им; длинные (2 400 удалённых веток) — с фильтром и не больше 200 строк. Стрелки и Enter выбирают; Escape закрывает только список: слой, который уже обработал клавишу, помечает её (`consume`), окно под ним её не трогает (так же теперь и с контекстным меню над окном).

## 4.15 Имена веток и регистр, сабмодули следом, статус наверху, Undo (2026-10-26)

- Поля ввода не меняют набранное: `autoCapitalize="none"`, без автокоррекции (WKWebView превращал `tmp/925_anr_fix` в `Tmp/925_anr_fix`), проверка орфографии только в многострочном тексте.
- Диск macOS не различает регистр: ветка — файл в `refs/heads`, и `Tmp/x` рядом с существующей папкой `tmp/` ложится в неё; git показывает `tmp/x`, а HEAD хранит `Tmp/x` — ни одна ветка не помечена текущей. Теперь: новая ветка (и новое имя при переименовании) берёт написание существующей папки (`storedBranchName`, при `core.ignorecase`), окно New branch предупреждает об этом; ветка, которую HEAD называет в другом регистре, считается текущей; переименование, меняющее только регистр, идёт через временное имя.
- Сабмодули следом (Preferences → General, по умолчанию включено): после checkout, pull, merge, rebase, reset, cherry-pick, revert и их Undo — `changedSubmodules(было, стало)`: сабмодули, чей записанный коммит изменился; обновляются (`submodule update --recursive` только для них, с подключением репозитория) лишь инициализированные и стоящие на прежнем записанном коммите; сдвинутые вручную остаются, о чём сообщается.
- Статус вверху, как в Fork (`ActivityBox` в середине панели, от 900 px): ветка, ↑/↓ относительно upstream (или «not published», «detached at …»), идущий merge/rebase; во время операции — её имя, процент, полоса и кнопка остановки (останавливает на самом деле: движок прерывает git, агент — свой стоп; результат «stopped» — не ошибка); ожидание блокировки; несколько секунд после — результат (✓ или ⚠ с переходом к ошибке). Кнопка остановки в строке состояния теперь тоже настоящая.
- Undo последнего действия: кнопка рядом со статусом (подпись — что будет отменено), ⌘Z вне полей ввода (в оболочке macOS Edit → Undo вызывает то же), More → Undo, палитра. Стек на репозиторий (до 30); запись помнит HEAD после действия — если HEAD с тех пор сдвинулся (коммит, checkout, команда в терминале), Undo отказывает и очищает стек, ничего не ломая. Что отменяется: stage / unstage / ханки / строки (индекс возвращается целиком: `write-tree` до, `read-tree` при отмене); discard файла, ханка, строк, всего (движок перед этим копирует файлы в `~/.prong/undo/<token>`, неделю; больше 200 МБ или 20 000 файлов — без отмены, о чём сказано); commit и amend (`reset --soft`, предупреждение, если коммит уже на сервере); checkout (назад; созданная им ветка удаляется, только если не сдвинулась); создание, удаление (вместе с upstream; удалённые на сервере остаются удалёнными), пакетное удаление и переименование веток; merge, pull, rebase, cherry-pick, revert (`reset --keep`, локальные изменения сохраняются); reset (soft/mixed — тем же режимом, hard — `--keep`; выброшенные hard-ом изменения не вернуть); stash (pop именно его) и drop stash (`stash store`); удаление тега (в том числе аннотированного).

## 4.16 Одна панель статуса справа вверху (2026-10-26)

- Поле командной палитры в панели инструментов убрано (палитра — ⌘K и пункт меню); на его месте справа — панель статуса (`StatusPanel`, ширина ~36 % окна, 240–560 px). Строки состояния внизу больше нет: всё, что она показывала, — здесь.
- Что в панели, по приоритету: идущая операция (имя, процент, полоса, остановка; клик — вывод git); очередь действий и ожидание блокировки (клик — список: отмена, удаление брошенной блокировки); последнее уведомление любого вида (успех, ошибка с «details» → окно ошибки, информация); загрузка; в покое — текущая ветка, ↑/↓ относительно upstream или «not published», merge/rebase в процессе с Continue и Abort. Справа — число ошибок сессии (журнал ошибок), «engine offline», Undo (⌘Z).
- На стартовом экране та же панель вверху справа (без ветки и Undo): уведомления, ошибки, состояние движка.
- В окне уже 1000 px кнопки панели инструментов становятся значками, чтобы панели статуса хватало места.
- Кнопки, открывающие меню или список (▾: стрелка у Commit, фильтр веток истории, выпадающие поля окон Fetch / Pull / Push, список веток у Push), — без обводки, только заливка; при наведении подсвечивается фон.

## 4.3 Что стало настоящим (вместо заглушек)

Работает через движок для живых репозиториев: открытие в редакторе / Finder / терминале (настройки External tools), история файла (`git log --follow`), blame (панель с авторами и переходом к коммиту), добавление в `.gitignore`, копирование путей и хешей в буфер, переименование ветки и upstream (диалоги), добавление / правка / удаление / prune remote, push тега, checkout тега и коммита (detached), rebase на произвольный коммит, abort merge/rebase и continue, сабмодули (раздел в сайдбаре: состояние, update/init, recursive, sync, открыть как репозиторий; в диффе указателя — subjects коммитов до/после), картинки, аудио и видео до/после в диффе (blob-эндпоинт с Range, см. 4.4), глобальная identity (`git config --global`), подпись коммитов (`commit.gpgsign`), режим pull по умолчанию, GitHub-аккаунт по токену (валидация через API, токен в Keychain) и device flow (нужен client id OAuth-приложения), список репозиториев GitHub при клонировании, загрузка публичного ключа в GitHub, SSH-ключи из `~/.ssh` (fingerprint, agent, passphrase), генерация ключа (`ssh-keygen`), добавление в агент, проверка `ssh -T`, агент через локальный Claude Code (stream-json, инструменты ограничены git/файлами; изменения интерфейса коммитятся в репозиторий исходников, версии = коммиты, revert/rollback = `git revert`).

Демо-репозитории убраны из начального состояния (2026-10-19): список репозиториев, аккаунты и ключи приходят только от движка; фикстуры в `src/git/mock` остаются для тестов и статической демо-сборки. Остались моками (помечены «(mock)» в тостах): провайдеры «Anthropic API key» и «OpenAI-compatible» для агента, «Both» при разрешении конфликта (нужен редактор слияния).

## 6. План этапов

1. **Прототип UI** — готов: все экраны на моках, кликабельная навигация, диалоги, анимации; запуск `npm run web`.
2. **Git-движок** — готов как локальный сервис (`npm run server`): настоящие репозитории в приложении (open/clone/init, граф, диффы, стейджинг, коммит, remote-операции с прогрессом, ветки, теги, merge/rebase/interactive rebase, stash, cherry-pick/revert/reset).
2a. **macOS standalone** — готов: `macos/build.sh` собирает `Prong.app` (Swift AppKit + WKWebView, веб-сборка и движок с портативным Node внутри, нативный выбор папок / Finder / Terminal через мост). Далее: Keychain для токенов, drag-drop папок, Developer ID + нотаризация, автозапуск движка с перезапуском при падении; затем переход окна на react-native-macos, когда его версия догонит RN проекта.
3. **Полный набор операций** — rebase-i, конфликты, stash, tags, blame, history, картинки в диффе, GitHub Device Flow, SSH-менеджер.
4. **Windows / Linux** — react-native-windows, Credential Manager; Linux через web-сборку в Tauri.
5. **Производительность** — профилирование на репозиториях 100k+ коммитов, инкрементальный граф, кэш диффов на диске.
